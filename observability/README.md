# Observability (spec §22-§25)

Metrics, logs, and one Grafana dashboard for CloudCrafter — built entirely on standard,
maintained Helm charts (`kube-prometheus-stack`, `loki-stack`) with values overrides in
this directory, per spec §22's explicit instruction not to hand-build a monitoring stack.

## Layout

```
observability/
├── prometheus/values.yaml   kube-prometheus-stack overrides (Prometheus + Grafana)
├── grafana/values.yaml      the grafana: sub-block of the same release (datasources sidecar, dashboard sidecar)
├── grafana/dashboards/cloudcrafter-dashboard.json   the dashboard itself
├── grafana/dashboard-configmap.yaml                 wraps the JSON for auto-provisioning
└── loki/values.yaml         grafana/loki-stack overrides (Loki + Promtail)
```

Grafana ships as a sub-chart of `kube-prometheus-stack`, so `prometheus/values.yaml` and
`grafana/values.yaml` are two files passed to the *same* `helm install`.

## Install

```sh
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

helm install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  -f observability/prometheus/values.yaml \
  -f observability/grafana/values.yaml

helm install loki grafana/loki-stack -n monitoring \
  -f observability/loki/values.yaml

kubectl apply -f observability/grafana/dashboard-configmap.yaml
```

## Metrics (spec §23)

Each service (`users`, `events`, `tickets`, `notifications`) uses `prom-client` to expose
`GET /metrics` with:
- `http_requests_total` (counter, labels: `method`, `route`, `status_code`)
- `http_request_duration_seconds` (histogram, same labels)
- default Node.js process metrics (CPU, memory, event loop, GC)

No secrets are ever used as metric label values (verified by a test per service).

Each service's Helm chart (`charts/{users,events,tickets,notifications}`) creates a
`ServiceMonitor` (gated by `serviceMonitor.enabled`, default `true`) so Prometheus
Operator discovers and scrapes `/metrics` on the named `http` Service port. Pod/node CPU
and memory come from `kube-state-metrics` + `node-exporter` + the kubelet's cAdvisor
endpoint, all enabled by default in `kube-prometheus-stack`.

## Logs (spec §24)

`loki-stack` (Loki + Promtail) ingests container stdout/stderr from every pod, including
the four CloudCrafter services, tagged with `namespace`/`pod`/`app` labels from
Kubernetes pod metadata. An audit of every `console.log`/`console.error` call across
`services/*` confirmed none logs private keys, passwords, JWT signing material, or
complete bearer tokens — only service-startup lines, notification records, and
non-sensitive S3 upload confirmations/errors.

## Grafana (spec §25)

- **Prometheus** datasource (uid `prometheus`) is auto-provisioned by
  `kube-prometheus-stack` as the default datasource.
- **Loki** datasource (uid `loki`) is auto-provisioned by the `loki-stack` chart's own
  sidecar-discovered ConfigMap — `observability/loki/values.yaml` pins its `isDefault`
  to `false` (it defaults to `true`, which collides with Prometheus's default and
  crashes Grafana on startup — "only one datasource per organization can be marked as
  default") and pins its `uid` to `loki` so the dashboard can reference it directly.
- The **CloudCrafter** dashboard (`grafana/dashboards/cloudcrafter-dashboard.json`) is
  auto-loaded via Grafana's dashboard sidecar from
  `grafana/dashboard-configmap.yaml` (labeled `grafana_dashboard: "1"`). It has a
  `$namespace` template variable (default/aws/google-cloud) and eight panels, all
  backed by real Prometheus/Loki queries — no hardcoded values:
  1. Service Health (`up{job=~"users|events|tickets|notifications"}`)
  2. Pod Readiness (`kube_pod_status_ready{condition="true"}`)
  3. Request Rate (`sum(rate(http_requests_total[5m])) by (job)`)
  4. Request Latency p95 (`histogram_quantile(0.95, ...http_request_duration_seconds_bucket...)`)
  5. Error Responses, 4xx/5xx (`sum(rate(http_requests_total{status_code=~"4..|5.."}[5m])) by (job, status_code)`)
  6. CPU Usage by Pod (`sum(rate(container_cpu_usage_seconds_total[5m])) by (pod)`)
  7. Memory Usage by Pod (`sum(container_memory_working_set_bytes) by (pod)`)
  8. CloudCrafter Logs (Loki query filtered to the four services)

Retrieve the Grafana admin password (auto-generated by the chart, never committed):

```sh
kubectl get secret -n monitoring kube-prometheus-stack-grafana \
  -o jsonpath='{.data.admin-password}' | base64 -d
```

## Verified

- All four services scraped and `up=1` in the `aws` and `google-cloud` namespaces after
  redeploying `charts/cloudcrafter` there with the new `ServiceMonitor`/named-port
  templates (the `default` namespace, being Argo CD-managed, picks this up on the next
  git-driven sync).
- A real traffic burst (mixed 200/201/400/401 responses) against the `aws` namespace
  produced live, non-zero values in all seven Prometheus-backed panels and 78 matching
  Loki log lines, queried directly through Grafana's `/api/ds/query` proxy.
- This environment's cAdvisor output has no per-container breakdown (only pod-level
  cgroup aggregates), so the CPU/memory queries filter on `pod!=""` rather than the more
  common `container!="", container!="POD"` pattern, which would silently return nothing
  here.
